# Data Structure and Relationships\n\n## Introduction\n\nThis document describes the conceptual data model for the Todo list application. It outlines what information the system stores, how different pieces of data relate to each other, and the lifecycle of that data from creation through deletion. This is a **business-focused description** of the data structure - it explains the \"what\" and \"why\" of data organization without prescribing technical implementation details like database schemas or tables.\n\nDevelopers have full autonomy to choose the appropriate database technology and schema design that best implements these conceptual relationships.\n\n---\n\n## Core Data Entities\n\nThe Todo application manages information across three primary entities:\n\n### 1. **User Account Entity**\nEvery person who uses the application has a user account. This represents their individual identity in the system and serves as the container for all their personal data. A user account is the foundational entity that enables all other functionality in the system.\n\n### 2. **Todo Item Entity**\nEvery task or item on a user's todo list is a distinct entity. Each todo item belongs to exactly one user and represents a single task that the user wants to track. Todo items are the core business entity that delivers value to users.\n\n### 3. **Session/Authentication Entity**\nWhen a user logs in, a session is created to represent their active authentication state. This allows the system to remember who the user is throughout their interaction with the application. Sessions manage the user's authenticated access and expire based on inactivity or logout.\n\n---\n\n## User Information\n\n### What Information is Stored About Each User\n\n#### User Identity Data\n- **User ID**: A unique identifier that distinguishes this user from all others in the system. Every user has exactly one User ID, and this ID never changes for that user's lifetime. Used throughout the system to associate data with the correct user.\n- **Email Address**: The user's email used for login and account recovery. This must be unique across all users - no two users can have the same email address. The email serves as the user's login identifier and primary contact method.\n- **Password**: The user's password used for authentication. Passwords are stored in a secure, encrypted format using cryptographic hashing and are never readable even by system administrators.\n\n#### User Account Metadata\n- **Account Created Date**: The date and time when the user first created their account. This value is set once at account creation and never changes. Serves as a permanent record of when the user joined the system.\n- **Last Active Date**: The most recent date and time the user logged in or interacted with the system. This updates each time the user accesses the application and is used to determine inactive accounts.\n- **Account Status**: Whether the account is active and usable, or has been deactivated/suspended. Most accounts are active; deactivation occurs only in special circumstances such as user request or administrative action.\n\n#### User Preferences and Settings\n- **Timezone (Optional)**: If needed for future date display features, the user's preferred timezone. Initially, this can be inferred from system defaults or IP location. When implemented, this ensures dates and times are displayed correctly for each user.\n- **Preferred Language (Optional)**: The user's preferred display language for the application interface. Enables internationalization and localization of the user experience.\n\n### User Data Isolation - Critical Business Requirement\n**WHEN a user logs in, THE system SHALL ensure that user can ONLY see, modify, or delete their own todos - never another user's todos. Each user's data is completely private and separate from all other users' data. This is enforced at every level of the system - from permission checks to database queries.**\n\n### User Account Lifecycle\n- **Creation**: User registers with email and password; account is created with \"Active\" status\n- **Active**: User can log in, create todos, modify todos, and manage their account\n- **Inactive**: Account still exists with all data intact, but user cannot log in (admin action)\n- **Deletion**: User or admin requests account deletion; account is marked for deletion and data is archived or removed per retention policy\n\n---\n\n## Todo Item Information\n\n### What Information is Stored for Each Todo\n\n#### Todo Identification\n- **Todo ID**: A unique identifier for this specific todo item. This ID uniquely identifies this todo among all todos in the entire system and never changes once created. Enables direct reference and access to specific todos.\n- **Owner User ID**: The User ID of the person who owns this todo. This field links each todo to its owner and enables the system to know which user's todo list contains this item. This relationship enforces data isolation and ownership.\n\n#### Todo Content and Description\n- **Title**: The main text or name of the todo item. This is the primary information the user sees when looking at their todo list and is the minimum required information. Example titles: \"Buy groceries\", \"Call dentist\", \"Finish project report\".\n- **Description (Optional)**: Additional details about the todo item beyond the title. This allows users to add more context and complexity. Example: \"Buy milk, eggs, bread, and vegetables at the supermarket\". This field is optional and may be left blank. Maximum 2000 characters to balance detail with storage efficiency.\n\n#### Todo Status\n- **Completion Status**: Whether the todo has been marked as complete or remains incomplete. This has exactly two possible states:\n  - **Incomplete**: The todo is still pending; the task has not been completed. Default state for newly created todos.\n  - **Complete**: The todo has been marked as done; the task is finished. User-determined state change.\n- **Completed Date (Conditional)**: If the todo has been marked complete, this field stores when the user marked it as complete using server timestamp. If the todo is still incomplete, this field has no value (null). Used for productivity tracking and understanding task completion patterns.\n\n#### Todo Organization and Metadata\n- **Created Date**: The date and time when the user first created this todo item. This is set automatically when the todo is created by the system and never changes. Provides an immutable creation timestamp for each todo.\n- **Last Modified Date**: The date and time of the most recent update to this todo item. This updates whenever the user edits the todo (title, description, or completion status). Enables the system to show recently modified todos or organize by modification recency.\n- **Order/Sequence**: A field that helps organize todos in a logical order on the user's list. Users may want their todos displayed in the order they created them, alphabetically, by completion status, or in a custom order. Supports multiple display preferences.\n\n### Todo Item Constraints and Validation Rules\n\nWHEN a user creates a todo item, THE system SHALL require the user to provide at minimum a title.\n\nTHE title SHALL contain at least 1 character (after trimming whitespace) and at most 255 characters, ensuring todos are concise yet descriptive.\n\nWHERE a description is provided, THE description SHALL contain at most 2000 characters, allowing detailed context without excessive storage demands.\n\nWHEN a todo item is marked as complete, THE system SHALL record the timestamp of when this completion occurred using server time (not client time) to maintain consistency.\n\nTHE title SHALL NOT consist entirely of whitespace characters; it must contain meaningful content.\n\n### Todo Item Lifecycle States\n- **New/Created**: Todo just created, incomplete status\n- **Active**: User interacts with todo (views, edits, marks complete/incomplete)\n- **Completed**: User marks todo as complete, completion timestamp is recorded\n- **Reactivated**: User marks completed todo as incomplete again, clearing completion timestamp\n- **Deleted**: User permanently removes todo; todo is removed from system\n\n---\n\n## Data Relationships\n\n### The User-to-Todo Relationship - Foundational Design\n\n**Fundamental Relationship**: Each user has many todos, and each todo belongs to exactly one user.\n\nThis is a **one-to-many relationship**:\n- **One side (User)**: A single user can own zero, one, or many todo items. A new user with no todos has an empty list. An active user might have dozens or hundreds of todos.\n- **Many side (Todo)**: A single todo item belongs to exactly one user. A todo cannot exist without an owner, and a todo cannot be shared between users or owned by multiple users.\n\n### Visual Representation of User-Todo Relationship\n\n```\nUser (One)\n  │\n  │ owns many\n  ├─→ Todo 1\n  ├─→ Todo 2\n  ├─→ Todo 3\n  └─→ ... many more\n\nEach Todo belongs to exactly One User\n```\n\n### Data Ownership and Privacy - Enforced Principle\n\n**WHEN a user attempts to view, modify, or delete a todo item, THE system SHALL verify that the requesting user is the owner of that todo. IF the user is not the owner, THE system SHALL deny the operation and return an appropriate error message.**\n\nThis fundamental enforcement ensures that:\n- User A cannot see user B's todos under any circumstance\n- User A cannot edit user B's todos even if they knew the todo ID\n- User A cannot delete user B's todos through any mechanism\n- Each user only ever interacts with their own data\n- Data isolation is technically enforced, not dependent on frontend security\n\n### Relationship via Owner User ID (Conceptual Foreign Key)\n\nTHE unique User ID that identifies each user is referenced in every todo item the user creates. This link ensures the system always knows which todos belong to which user and allows the system to retrieve all of a user's todos efficiently. The Owner User ID field in the Todo entity logically points back to the owning User entity.\n\n### Relationship Implications\n\nWHEN a user account is deleted, THE system SHALL also handle all todos associated with that user according to data retention policies (deletion, archival, or anonymization).\n\nWHEN a user creates a new todo, THE system SHALL automatically associate it with the authenticated user's User ID, preventing users from creating todos for other users.\n\nWHEN a user requests their todo list, THE system SHALL filter by their User ID, ensuring only their own todos are returned.\n\n---\n\n## Data Lifecycle\n\n### Phase 1: Creation Phase\n\n#### User Account Creation\nWHEN a person signs up for the application, a new User record is created containing:\n- A newly generated unique User ID\n- The provided email address (verified for uniqueness)\n- The provided password (encrypted using secure hashing)\n- Current timestamp as Account Created Date\n- \"Active\" status as Account Status\n- Current timestamp as Last Active Date (representing account creation)\n\nThe account is immediately set to \"Active\" status and is ready for use.\n\n#### Todo Item Creation\nAt any point after logging in, a user can create a new todo item. WHEN created:\n- THE system assigns a unique Todo ID to the new item\n- THE system records the current UTC date/time as the Created Date\n- THE system links the todo to the user's User ID (establishing ownership)\n- THE system sets the completion status to \"Incomplete\"\n- THE system initializes the Completed Date field to null (no completion yet)\n- THE system sets the Last Modified Date to match Created Date\n- THE todo appears immediately on the user's list\n\n### Phase 2: Active/Modification Phase\n\nWhile a todo exists and has not been deleted, a user can perform multiple actions:\n\n**Viewing**: User can view the todo's information at any time. THE system returns complete todo details including title, description, status, and all timestamps.\n\n**Updating Title or Description**: User can change the task content. WHEN an update occurs:\n- THE system modifies the title or description as requested\n- THE system updates the Last Modified Date to current time\n- THE system preserves the original Created Date unchanged\n- THE system preserves the completion status unchanged (unless changed through completion operation)\n- THE modification is immediately reflected in the user's list\n\n**Marking as Complete**: User can change the status from \"Incomplete\" to \"Complete\". WHEN this occurs:\n- THE system updates the Completion Status to \"Complete\"\n- THE system records the Completed Date to current UTC time\n- THE system updates the Last Modified Date to current time\n- THE todo remains in the list with visual indication of completion\n- THE user can still edit the completed todo if needed\n\n**Marking as Incomplete**: User can revert a completed todo back to incomplete status. WHEN this occurs:\n- THE system updates the Completion Status to \"Incomplete\"\n- THE system clears the Completed Date (sets to null)\n- THE system updates the Last Modified Date to current time\n- THE todo returns to the incomplete todos section of the list\n- THIS allows users to reopen todos that were marked complete in error\n\n### Phase 3: Deletion Phase\n\nWHEN a user explicitly deletes a todo, THE system SHALL:\n- Remove the todo item from the system permanently\n- THE user no longer sees the todo in their list\n- THE user cannot recover the deleted todo\n\n**Note**: In the initial minimum viable version, deleted todos are simply removed from the system. Future versions might implement a \"trash\" or \"archive\" feature to recover recently deleted items, but this is not part of minimum functionality. The current approach prioritizes simplicity.\n\n### Phase 4: User Account Deletion (Extended Lifecycle)\n\nIF a user requests their account to be deleted, THE system SHALL:\n- Soft delete the user account (mark as deleted rather than immediately remove)\n- Mark all associated todos for deletion or archive them\n- Remove user's personal information (email, preferences)\n- Preserve audit trail data for compliance\n- Prevent the deleted user from logging in\n- After retention period, permanently delete account and todos\n\n### Complete Lifecycle Timeline Example\n\n```\nT1: User creates account\n    └─ User ID assigned, Account Created Date = T1\n\nT2: User creates first todo\n    └─ Todo ID assigned, Created Date = T2, Status = Incomplete\n\nT3: User edits todo title\n    └─ Last Modified Date = T3 (Created Date stays at T2)\n\nT4: User completes todo\n    └─ Status = Complete, Completed Date = T4, Last Modified Date = T4\n\nT5: User marks todo incomplete again\n    └─ Status = Incomplete, Completed Date = null, Last Modified Date = T5\n\nT6: User creates second todo\n    └─ New Todo ID assigned, Created Date = T6\n\nT7: User deletes first todo\n    └─ Todo permanently removed from system\n\nT8: User deletes account\n    └─ Account marked for deletion, all remaining todos handled per retention policy\n```\n\n---\n\n## Data Retention Policies\n\n### User Account Data Retention\n\n**Active Accounts**: User account information is retained indefinitely as long as the account is active and not deleted by the user. User data includes email, encrypted password, account status, and account timestamps. All user data is preserved to enable continued use of the application.\n\n**Inactive Accounts**: Accounts with no activity for extended periods (not defined in minimum viable version, but could be 1-2 years) may be flagged for potential cleanup, but are not automatically deleted.\n\n**Deleted Accounts**: IF a user requests account deletion, THE system SHALL:\n- Mark the account as deleted immediately\n- Remove personally identifiable information (email, profile data) after archive\n- Archive audit logs that reference the deleted user (for compliance)\n- Permanently delete the account record after retention period (typically 30-90 days)\n- Permanently delete all associated todos after same retention period\n\n### Todo Item Data Retention\n\n**Active Todos**: Todo items are retained indefinitely until the user explicitly deletes them. Completed todos are retained in the system and remain visible on the user's list. Users may review completed todos at any time to track their history of accomplishments.\n\n**Deleted Todos**: THE system SHALL NOT retain deleted todos. Once a user deletes a todo, that data is permanently removed immediately and cannot be recovered. Audit logs may contain reference to the deletion, but not the todo content.\n\n**Archived Todos**: Not implemented in minimum viable version, but could allow users to archive completed todos for reference without cluttering the active list.\n\n### Session and Authentication Data Retention\n\n**Active Sessions**: When a user logs in, a session is created and maintained. THE session is retained while the user is actively using the application and is used to authenticate all API requests during that session.\n\n**Expired Sessions**: WHEN a user logs out, THE system SHALL immediately terminate that session and revoke associated tokens. THE session data is no longer needed. IF a session remains inactive for an extended period (default 30 minutes but configurable), THE system SHALL automatically expire that session and require re-authentication.\n\n**Logout Sessions**: Session records may be retained in audit logs for security review purposes (typically 90 days) even after session termination, but the actual session tokens are invalidated immediately.\n\n### Audit Log Data Retention\n\n**Retention Duration**: Audit logs are retained for minimum 90 days by default, with configurable retention periods up to 2 years for compliance purposes.\n\n**Scope**: Audit logs contain records of:\n- User authentication events (login, logout, password reset)\n- Todo creation, modification, deletion events\n- User account management actions\n- Admin operations and system changes\n\n**Immutability**: Audit logs are immutable; once created, they cannot be modified or deleted (except through automatic retention policy cleanup).\n\n---\n\n## Data Organization Principles\n\n### Primary Organization: By Owner (User ID)\n\nAll data in the system is fundamentally organized by owner (the User ID). THE system always groups todos by their owning user. This organization ensures:\n- **Efficient Data Retrieval**: Fetching one user's todos requires a simple filter by User ID\n- **Complete Data Isolation**: Each user's data is logically and physically separated\n- **Clear Ownership Boundaries**: Every piece of data has an unambiguous owner\n- **Privacy Protection**: Accidental data leakage is prevented through structural design\n\nWHEN querying the database, THE system SHALL always include a User ID filter to ensure users only access their own data.\n\n### Secondary Organization: Within a User's List\n\nFor each user's todos, the system can organize the list according to user needs:\n\n**Default Ordering**: Todos are displayed in multiple possible orders:\n- **By Creation Date (Most Common)**: Newest todos first (most recent creation) or oldest first (chronological)\n- **By Completion Status**: Incomplete todos listed first, completed todos grouped separately, enabling easy focus on pending work\n- **By Modification Date**: Recently updated todos shown prominently, useful for finding todos the user recently worked on\n- **By Title (Alphabetical)**: Todos sorted alphabetically, useful for locating specific todos by name\n- **Custom Order (Future)**: Users may manually arrange todos in preferred sequence\n\nTHE system SHALL support flexible sorting to adapt to different user work styles and preferences.\n\n**Grouping Strategies**: Todos for a single user can be conceptually grouped by:\n- **Completion Status**: Incomplete vs. Complete, enabling focus on work needed\n- **Other Attributes (Future)**: Categories, tags, projects, or due date ranges (not in minimum version)\n\n**Pagination**: For users with many todos, THE system SHALL organize them into pages of 20-50 items, enabling efficient display and navigation.\n\n### Uniqueness and Identification\n\n**User ID Uniqueness**: Within the system, each user is uniquely identified by their User ID. No two users have the same ID. THE system generates User IDs using UUID or similar mechanism to ensure global uniqueness.\n\n**Email Uniqueness**: Each user's email address is unique within the system. THE system validates during registration that no other account uses the requested email. This ensures:\n- Email-based login works correctly (no ambiguity about which account to access)\n- Account recovery via email is unambiguous\n- Communication with users can reach exactly one account\n\n**Todo ID Uniqueness**: Each todo item has a unique Todo ID. This ID is globally unique across the entire system and all users. This allows any component of the system to directly reference a specific todo without ambiguity, even if two users have todos with identical titles.\n\n### Search and Filter Organization\n\nTHE system SHALL support searching and filtering todos:\n\n**Search**: Users can search for todos by keyword in title or description, enabling quick location of specific items in large lists.\n\n**Filter**: Users can filter todos by:\n- Completion status (show only incomplete, show only completed, show all)\n- Creation date range (todos created in last week, month, year)\n- Modification date range (todos modified recently)\n\nTHESE search and filter capabilities organize data dynamically based on user query rather than fixed storage organization.\n\n---\n\n## Metadata and Timestamps\n\n### Why Timestamps Matter in Business Context\n\nTimestamps (dates and times) are recorded for several important business reasons:\n\n1. **Audit Trail and Accountability**: They help track when changes occurred, providing a complete historical record of system activity for troubleshooting and compliance.\n2. **User Experience**: They help display todos in meaningful order (newest first, recently modified, etc.) that matches user expectations.\n3. **Completion Tracking**: They track when users completed tasks, potentially enabling future productivity analysis or helping users understand their work patterns.\n4. **Account Security**: They help detect suspicious account activity by tracking login patterns and identifying anomalies.\n5. **Data Lifecycle Management**: They enable automatic cleanup of expired sessions and data archival based on age.\n\n### Required Timestamps\n\n#### For User Accounts\n**Account Created Date**: When the account was first created (never changes after initial creation). Represents the user's tenure in the system.\n\n**Last Active Date**: When the user last logged in or performed an action. Updates with each user interaction. Used to identify inactive accounts and understand user engagement.\n\n**Last Login Date**: More specifically, the timestamp of the user's most recent login event. Distinct from Last Active Date in that login is a specific event rather than general activity.\n\n#### For Todo Items\n**Created Date**: When the todo was created (never changes after initial creation). Represents the age of the todo and when the user first thought of this task.\n\n**Last Modified Date**: When the todo was last changed - when title/description was edited or completion status was updated. Updates each time any todo property changes. Helps identify recently worked-on todos.\n\n**Completed Date**: When the user marked the todo as complete (only set if todo is completed, otherwise null). Tracking when tasks are completed enables productivity analysis and helps users see patterns of accomplishment.\n\n### Timestamp Accuracy and Format Requirements\n\nTHE system SHALL record all timestamps in a consistent format and timezone. All timestamps are stored in UTC (Coordinated Universal Time) internally to ensure consistency across time zones and server locations. WHILE displaying timestamps to users, THE system MAY convert to their local timezone for readability, but the source-of-truth storage is always UTC.\n\n**Timestamp Format**: ISO 8601 format (e.g., \"2025-11-14T22:01:14Z\") provides international standard for date-time representation.\n\n**Server-Side Generation**: THE system SHALL ALWAYS generate timestamps on the server (not trusting client-provided timestamps) to prevent clock skew issues and ensure data consistency.\n\n### Timestamp Usage Examples\n\n**Example 1**: User creates todo at 10:00 AM UTC\n- Created Date = 2025-11-14T10:00:00Z\n- Last Modified Date = 2025-11-14T10:00:00Z\n- Completed Date = null\n\n**Example 2**: User edits todo title at 2:30 PM UTC\n- Created Date = 2025-11-14T10:00:00Z (unchanged)\n- Last Modified Date = 2025-11-14T14:30:00Z (updated)\n- Completed Date = null (unchanged)\n\n**Example 3**: User marks todo complete at 5:00 PM UTC\n- Created Date = 2025-11-14T10:00:00Z (unchanged)\n- Last Modified Date = 2025-11-14T17:00:00Z (updated)\n- Completed Date = 2025-11-14T17:00:00Z (now set)\n\n---\n\n## Summary: Complete Data Model Overview\n\n### Entity Relationship Diagram Ownership Clarity**: Every todo has a clear owner (the User ID). No ambiguity about who owns what data.\n\n**2. Immutability Where It Matters**: Created dates and User IDs never change, providing stable references and audit trail.\n\n**3. Mutability for Active Use**: Title, description, completion status, and last modified date can change, supporting ongoing user interaction.\n\n**4. Null/Optional Fields**: Description, completed date, and other optional fields are truly optional; null values are valid.\n\n**5. Complete Data Isolation**: Every query, update, and delete operation verifies the requesting user owns the target data.\n\n**6. Extensibility Without Breaking**: The data model is designed so future features (categories, tags, due dates, etc.) can be added without modifying core entities.\n\n---\n\n## Conceptual Data Flow Through System\n\n### User Registration and Initial State\n\n1. User visits application → User not yet registered\n2. User enters email and password → System validates input\n3. System creates User record with:\n   - New User ID\n   - Email address (validated for uniqueness)\n   - Encrypted password\n   - Current timestamp as Account Created Date\n   - Account status = \"Active\"\n4. User account is created empty (no todos exist yet)\n5. System sends confirmation email\n6. User is ready to create todos\n\n### User Activity and Data Changes Flow\n\n1. User logs in → System authenticates using email/password\n2. System returns JWT token linking to User ID\n3. User creates first todo → System creates Todo record, links to User ID\n4. User creates additional todos → System creates Todo records, all linked to same User ID\n5. User edits todo title → System updates Todo, increments Last Modified Date\n6. User marks todo complete → System sets Completed Date, updates Status and Last Modified Date\n7. User marks todo incomplete → System clears Completed Date, updates Status and Last Modified Date\n8. User deletes todo → System removes Todo permanently\n9. User logs out → System terminates Session, updates Last Active Date\n10. User logs in again later → System authenticates again, creates new Session\n\n### Data Integrity Throughout Lifecycle\n\n- THE system SHALL maintain the link between each todo and its owner throughout the todo's entire lifecycle\n- THE system SHALL update timestamps accurately as changes occur, using server time\n- THE system SHALL prevent any user from accessing another user's data at any point\n- THE system SHALL enforce all data validation rules (title length, description limits, format requirements)\n- THE system SHALL not allow users to modify ownership or create todos for other users\n- THE system SHALL preserve complete audit trail of who created, modified, and deleted each piece of data\n\n---\n\n## Data Model Extensibility\n\nThe core data model is designed to support future enhancements without breaking changes:\n\n**Future Todo Features** could be added without modifying core Todo entity:\n- Due dates and reminders\n- Priority levels\n- Categories or projects\n- Tags or labels\n- Subtasks\n- Attachments or file references\n\n**Future User Features** could be added without modifying core User entity:\n- User profile information\n- Preferences and settings\n- Notification preferences\n- Account recovery options\n\n**Future Collaboration Features** could be added with new entities:\n- Shared todo lists\n- Collaboration invitations\n- User permissions on shared items\n\nThe one-to-many relationship between Users and Todos is the stable core upon which all features build.\n\n---\n\n> *Developer Note: This document defines the **conceptual data model and business relationships only**. All technical database design, schema implementation, query optimization, indexing strategies, and data persistence mechanisms are at the discretion of the development team. Developers should design the actual database schema and relationships to efficiently implement this conceptual model while meeting performance and scalability requirements defined in other documents.*"
