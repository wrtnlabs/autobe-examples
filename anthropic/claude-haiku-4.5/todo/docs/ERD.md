### `todo_app_users`

User accounts representing individuals who authenticate and manage their
own todo lists. Each user has unique identity (email), secure password
hash, account status tracking, and temporal audit fields. Users form the
primary identity entity for the application.

Properties as follows:

- `id`: Primary Key.
- `email`
  > User's email address for authentication and communication. Must follow
  > valid email format (RFC 5322). Used as the unique login identifier for
  > the user account.
- `password_hash`
  > Securely hashed password using bcrypt or Argon2. Never stored in
  > plaintext. Used to verify user identity during authentication. Hash is
  > generated server-side from user's plaintext password input.
- `status`
  > Current account status indicating whether user can access the system.
  > Valid values: 'active' (user can log in and access todos), 'inactive'
  > (user cannot log in, data preserved). Defaults to 'active' on account
  > creation.
- `created_at`
  > Timestamp when the user registered and created their account.
  > Automatically set by system at account creation time. Never changes after
  > creation. Stored in UTC timezone.
- `updated_at`
  > Timestamp of the most recent update to any user profile field (excluding
  > session/activity fields). Automatically updated whenever user information
  > changes. Stored in UTC timezone.
- `deleted_at`
  > Timestamp indicating when the user account was deleted (soft delete).
  > NULL means account is active. When set, user cannot log in but data is
  > preserved for audit trail and recovery. Stored in UTC timezone.

### `todo_app_todos`

Core todo item entity representing individual tasks managed by users.
Each todo belongs exclusively to one user and tracks the complete
lifecycle from creation through completion. Todos contain required
properties (title, status) and optional properties (description,
priority, due_date). Timestamps track creation, modification, and
completion events. This entity is the central business object enabling
users to capture, organize, and track their work.

Properties as follows:

- `id`: Primary Key.
- `todo_app_user_id`
  > Owner user's [todo_app_users.id](#todo_app_users). Establishes one-to-many
  > relationship where each todo belongs to exactly one user and user can
  > have many todos.
- `title`
  > Required todo title/description that identifies what the user needs to
  > do. Maximum 255 characters, must be non-empty. Primary identifier for the
  > todo from user perspective.
- `description`
  > Optional detailed information and context about the todo. Additional
  > notes beyond the title. Maximum 2000 characters. Can be empty if user
  > does not provide additional details.
- `status`
  > Current state of the todo. Only two valid values: 'active' for incomplete
  > todos, 'completed' for finished todos. Defaults to 'active' when created.
  > Determines visibility in active vs completed todo lists.
- `priority`
  > Optional importance level of the todo. Valid values: 'low', 'medium',
  > 'high'. Defaults to 'medium' if not specified by user. Helps users
  > prioritize their work.
- `due_date`
  > Optional target completion date for the todo in ISO 8601 format
  > (YYYY-MM-DD). Must not be in the past. If provided, helps users manage
  > deadlines. Can be null when no specific deadline exists.
- `created_at`
  > System-generated timestamp in UTC when the todo was created. Immutable
  > after creation, never changes. Records when user captured the task.
- `updated_at`
  > System-generated timestamp in UTC of the most recent modification.
  > Updated every time any field of the todo changes. Enables tracking of
  > recent activity and recency sorting.
- `completed_at`
  > System-generated timestamp in UTC when the todo was marked as completed.
  > Only populated when status is 'completed'. Automatically cleared when
  > status changes back to 'active'. Records when user finished the task.
