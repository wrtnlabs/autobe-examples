## Primary User Journey

This document describes the complete, linear user journey for the Todo List application—from the moment a user first interacts with the system to their daily use. This journey is designed with strict minimalism in mind: no drag-and-drop, no sorting, no categories, no bulk operations. Every interaction is atomic and focused on a single task. This journey ensures backend developers understand the exact sequence of user actions and system responses.

### Onboarding Experience

WHEN a user accesses the application for the first time, THE system SHALL display a simple login screen. THE system SHALL NOT display any tutorials, welcome messages, or tooltips. THE system SHALL NOT offer guest access. THE user SHALL be required to create an account with a valid email address and password. THE user SHALL be able to register only once per email address. IF the email address is already registered, THEN THE system SHALL display the message: "An account with this email already exists. Please log in." WHERE the user has previously registered, THE system SHALL allow authentication with stored credentials. WHERE the user has never registered, THE system SHALL require the user to complete the registration process before proceeding.

### Creating a New Todo Item

WHEN the user is logged in, THE system SHALL display their personal todo list in a plain, unformatted list. WHEN the user clicks on the "Add Todo" button, THE system SHALL display a text input field with placeholder text: "What needs to be done?". WHEN the user enters text and presses Enter or clicks "Add", THE system SHALL validate the input. IF the input is empty or contains only whitespace, THEN THE system SHALL display the message: "Please enter a task description." and do not create the item. IF the input exceeds 255 characters, THEN THE system SHALL display the message: "Task description cannot exceed 255 characters." and do not create the item. WHEN the input is valid, THE system SHALL create a new todo item with the following properties: id (UUID), text (user input), completed (false), createdAt (ISO timestamp), updatedAt (ISO timestamp), and ownerId (authenticated user ID). THE system SHALL immediately append the new item to the bottom of the list. THE system SHALL NOT apply any sorting, prioritization, or grouping to the new item. THE system SHALL NOT automatically focus or select the new item. THE system SHALL clear the input field after successful creation.

### Viewing the Todo List

WHILE the user is logged in, THE system SHALL display all of the user's todo items in the order they were created (oldest at the top, newest at the bottom). THE system SHALL load the full list of items on initial page load. THE system SHALL not load items in pages or with pagination. THE system SHALL not filter or search the list. THE system SHALL not group items by status or date. WHERE the user has no todo items, THE system SHALL display the message: "No tasks yet. Add one above!". THE system SHALL load all items for the authenticated user based on their ownerId. THE system SHALL NOT display items belonging to any other user. THE list SHALL update immediately after item creation, update, or deletion. THE system SHALL display each item as a single line with the text, followed by a checkbox (unchecked for incomplete, checked for complete).

### Marking a Todo as Complete

WHEN the user clicks the checkbox next to a todo item, THE system SHALL toggle the completed status of that item. IF the item was incomplete, THEN THE system SHALL set completed to true. IF the item was complete, THEN THE system SHALL set completed to false. THE system SHALL immediately update the visual state of the checkbox without requiring a page reload. THE system SHALL NOT reorder items when completed status changes. THE system SHALL NOT fade, hide, or strike through completed items—they SHALL remain visible in place. THE system SHALL NOT automatically check the box when a user types in an edit field—it SHALL only respond to checkbox clicks. THE system SHALL verify that the item being updated belongs to the currently authenticated user before making any change. IF the user attempts to toggle a todo item that does not belong to them, THEN THE system SHALL return an error message: "You cannot modify another user's task." and make no change.

### Editing an Existing Todo

WHEN the user double-clicks the text of a todo item, THE system SHALL replace the displayed text with an editable text input field pre-filled with the current content. WHEN the user modifies the text and presses Enter or clicks "Save", THE system SHALL validate the new input. IF the new text is empty or contains only whitespace, THEN THE system SHALL display the message: "Task description cannot be empty." and revert to the original text. IF the new text exceeds 255 characters, THEN THE system SHALL display the message: "Task description cannot exceed 255 characters." and revert to the original text. WHEN the input is valid, THE system SHALL update the item's text property and set the updatedAt field to the current timestamp. THE system SHALL NOT allow partial edits while the user is typing—confirmation SHALL be required via Enter or Save button. THE system SHALL NOT create a new item during editing. THE system SHALL preserve the original id and createdAt fields. THE system SHALL verify before updating that the item belongs to the currently authenticated user. IF the user attempts to edit a todo item that does not belong to them, THEN THE system SHALL return an error message: "You cannot modify another user's task." and make no change.

### Deleting a Todo

WHEN the user clicks the "Delete" button next to a todo item, THE system SHALL display a confirmation dialog with the message: "Are you sure you want to delete this task? This action cannot be undone." WHEN the user confirms, THE system SHALL immediately remove the item from the database and the displayed list. THE system SHALL NOT move the item to a "trash" folder. THE system SHALL NOT archive or hide the item. THE system SHALL NOT allow recovery of deleted items. THE system SHALL verify before deletion that the item belongs to the currently authenticated user. IF the user attempts to delete a todo item that does not belong to them, THEN THE system SHALL return an error message: "You cannot delete another user's task." and make no change. THE system SHALL remove the item from the DOM immediately after server confirmation. THE system SHALL not renumber or reposition remaining items.

### Logging Out

WHEN the user clicks the "Log Out" button, THE system SHALL send a logout request to the server. THE system SHALL immediately invalidate the user's JWT and clear all stored tokens from local storage. THE system SHALL redirect the user to the login screen. THE system SHALL NOT preserve the current list of todos or any session state. THE system SHALL NOT show any "See you soon!" messages. The user SHALL be fully logged out and returned to an anonymous state.

### Returning After Logout

WHEN a previously registered user returns to the application after logging out, THE system SHALL display the same login screen as during onboarding. THE user SHALL be required to re-enter their email and password. THE system SHALL NOT auto-fill credentials unless the user previously chose to save them in the browser. THE system SHALL NOT restore any state from the previous session—no todos, no scroll position, no selected items. THE list SHALL load only after successful re-authentication and SHALL be populated with items belonging ONLY to the authenticated user's ID. THE system SHALL NOT assume the user is the same person if a different email is entered—even if the browser remembers credentials.
