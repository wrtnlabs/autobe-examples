### `todo_list_configurations`

System-wide configuration settings and feature flags governing
application behavior and operational parameters.

Stores key-value pairs that control application features, operational
parameters, and behavioral settings across the entire system. These
configurations are managed by administrators through administrative
interfaces and affect system-wide behavior rather than individual user
experience.

Configuration values can control feature toggles, rate limits, timeouts,
external service endpoints, and other operational settings. The enabled
flag allows administrators to activate or deactivate configurations
without deleting them, maintaining audit trails for compliance.

This table is referenced by various system components to determine their
runtime behavior based on centralized configuration.

Properties as follows:

- `id`: Primary Key.
- `configuration_key`
  > Unique identifier for the configuration setting (e.g.,
  > "feature_toggles.new_ui", "api.rate_limit.per_minute"). Must be unique
  > across all configurations.
- `configuration_value`
  > The actual value of the configuration setting. Can represent boolean
  > ("true"/"false"), numbers, strings, JSON objects, or any other data
  > format. Stored as string to accommodate any configuration type.
- `description`
  > Detailed explanation of what this configuration controls, its expected
  > values, and its impact on system behavior. Used by administrators to
  > understand configuration purpose.
- `enabled`
  > Whether this configuration is active and affecting system behavior. When
  > false, the system should ignore this configuration regardless of its
  > value.
- `created_at`
  > Timestamp when this configuration was created. Used for audit trail and
  > debugging purposes.
- `updated_at`
  > Timestamp when this configuration was last modified. Updated
  > automatically on any change to the configuration.
- `deleted_at`
  > Timestamp when this configuration was logically deleted. Used for soft
  > deletion to maintain audit trails while allowing configurations to be
  > deactivated without permanent deletion.

### `todo_list_tokens`

Authentication tokens (access and refresh) issued to users, tracking
validity, expiration, and revocation status.

Manages the lifecycle of tokens associated with authenticated sessions.
Each token is linked to exactly one session (user, admin, or guest) and
contains either an access token or refresh token value.

Access tokens are short-lived and used for API authentication, while
refresh tokens are longer-lived and used to obtain new access tokens when
expired. The system tracks token expiration and revocation to enforce
secure authentication policies.

Tokens are automatically revoked when users log out or when sessions
expire. The revoked_at field allows for explicit revocation before
expiration and supports audit trails of security incidents.

Properties as follows:

- `id`: Primary Key.
- `todo_list_user_session_id`: Session that issued this token. [todo_list_user_sessions.id](#todo_list_user_sessions).
- `todo_list_admin_session_id`: Session that issued this token. [todo_list_admin_sessions.id](#todo_list_admin_sessions).
- `todo_list_guest_session_id`: Session that issued this token. [todo_list_guest_sessions.id](#todo_list_guest_sessions).
- `token_type`
  > Type of authentication token: 'access' for short-lived API tokens,
  > 'refresh' for long-lived token renewal tokens. Cannot be null - every
  > token must be explicitly classified.
- `token_value`
  > The actual cryptographic token value issued for authentication. Must be a
  > secure, random string that cannot be guessed. Used to authenticate API
  > requests.
- `expires_at`
  > The exact timestamp when the token expires and becomes invalid. This is a
  > required security field - sessions cannot grant unlimited access. All
  > tokens must have an expiration time.
- `revoked_at`
  > The timestamp when the token was explicitly revoked before expiration.
  > NULL means token has not been voluntarily revoked. Used for audit trails
  > when users log out or security events occur.
- `created_at`
  > The timestamp when this token was originally issued and stored in the
  > database.
- `updated_at`
  > The timestamp when this token was last modified (typically updated when
  > revoked).

### `todo_list_user`

Authenticated user account with email, password hash, and profile
information.

Represents the primary identity record for users who can log in to the
system and manage personal todo lists.

Each user has a unique email address for authentication, and their
password is stored as a hashed value for security. The table maintains a
soft delete capability to preserve audit trails while allowing account
deactivation.

This actor entity has a one-to-many relationship with
todo_list_user_sessions, which tracks all login sessions for the user.

User accounts are created through registration workflow and are never
shared between users.

Properties as follows:

- `id`: Primary Key.
- `email`
  > User's unique email address used for authentication and communication.
  > Must be unique across all users.
- `password_hash`
  > Hashed password for authentication. Never stored in plain text. Generated
  > using strong hashing algorithm with salt.
- `created_at`: Timestamp when the user account was created.
- `updated_at`: Timestamp when the user account was last updated.
- `deleted_at`
  > Timestamp when the user account was soft-deleted. Null indicates account
  > is active.

### `todo_list_guest`

Represents unauthenticated visitors with no account data - used only for

This actor type enables the system to track and maintain state for
anonymous users who interact with public content. Unlike authenticated
users, guest actors don't have login credentials or persistent profiles,
but still require a unique identifier and session tracking to maintain
temporary state across HTTP requests.

The guest entity provides a consistent actor pattern across all user
types in the system, allowing unified authentication flows and session
management even for anonymous access. Guest records are temporary and
typically persist only for the duration of a browsing session.

Properties as follows:

- `id`: Primary Key.
- `created_at`
  > Timestamp when this guest actor record was created. Mandatory for
  > tracking session lifecycle.
- `updated_at`
  > Timestamp when this guest actor record was last updated. Used for session
  > activity tracking.

### `todo_list_user_sessions`

Authentication sessions for authenticated todo_list_user accounts,
tracking login state, connection context, and session expiration.

Each session represents a single authenticated login event from a user.
The table captures essential connection details (IP address, request URL,
referrer) and enforces session lifetime through mandatory expiration.

Sessions are append-only - never updated or soft-deleted. Instead,
expired sessions are purged by system maintenance. Primary purpose is
security: limiting concurrent sessions and detecting suspicious access
patterns.

The user_id foreign key references todo_list_user.id, establishing
ownership. Any new login creates a new session record, preserving
historical access patterns for auditing.

Properties as follows:

- `id`: Primary Key.
- `user_id`: The authenticated user this session belongs to. [todo_list_user.id](#todo_list_user).
- `ip`: IP address from which the session was initiated.
- `href`: The full URL requested when this session was created.
- `referrer`: The website or application that referred the user to this system.
- `created_at`: Timestamp when this session was created (first login event).
- `expired_at`
  > Timestamp when this session expires and becomes invalid. Sessions must
  > expire for security - unlimited sessions are prohibited.

### `todo_list_admin_sessions`

Authentication sessions for todo_list_admin, tracking tokens and login
states.

Tracks active and expired login sessions for administrative users of the
system. Each session records the connection context (IP address, URL,
referrer) and timestamps for session lifecycle management.

Session records are append-only for audit trail purposes and do not
represent user identity information (which resides in the todo_list_admin
table). When a session expires, its expired_at field is set to the
timestamp of expiration, after which it is no longer considered valid for
authentication purposes.

Sessions are automatically created during login and terminated during
logout or automatically after a system-defined timeout period.

Properties as follows:

- `id`: Primary Key.
- `admin_id`: Admin actor's [todo_list_admin.id](#todo_list_admin).
- `ip`: Client IP address from which the session was initiated.
- `href`: Connection URL (path and query parameters) that initiated the session.
- `referrer`: Referrer URL indicating the source that redirected the user to the system.
- `created_at`: Timestamp when this session was created and validated.
- `expired_at`
  > Timestamp when this session expired. Sessions must expire for security
  > reasons. Non-null by default.

### `todo_list_todos`

Individual todo items owned by authenticated users with title, completion
status, and timestamps.

Each todo item represents a discrete task that a user creates, manages,
and completes within their personal todo list. Todo items are
intrinsically linked to the user who created them through a foreign key
relationship, ensuring complete data isolation between users.

Items support full lifecycle management: creation with title, toggling
completion status, and deletion. All modifications are tracked with
precise timestamps. Soft deletion is implemented to maintain audit trails
while allowing user-initiated removal.

This table is fundamental to the Todo component's core functionality,
providing persistent storage for user-specific task data without
duplicating user authentication information.

Properties as follows:

- `id`: Primary Key.
- `todo_list_user_id`: The user who owns this todo item. [todo_list_user.id](#todo_list_user).
- `title`
  > Title of the todo item (1-500 characters). The primary identifier for the
  > task that users enter and manage.
- `completed`
  > Completion status of the todo item. True indicates the task is marked
  > complete, false indicates it is still pending.
- `created_at`
  > Timestamp when this todo item was created. Always set to current time on
  > creation and never modified afterwards.
- `updated_at`
  > Timestamp when this todo item was last modified. Updated on any change to
  > title or completion status.
- `deleted_at`
  > Timestamp when this todo item was soft-deleted by the user. NULL
  > indicates the item is still active. Used to support undelete
  > functionality and audit trails.
